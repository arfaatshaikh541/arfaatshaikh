# Technology Stack — Evaluated Choices

Format per decision: selected technology, alternatives considered, reason, security
consequences, operational consequences, vendor lock-in, migration path. These are
**Milestone-0-appropriate recommendations**, not final commitments — each becomes a
formal ADR (`docs/adr/`) at the point it's actually adopted, and can be revisited.

## Durable workflow / agent orchestration

- **Selected**: Temporal (self-hostable) for durable workflow execution; a thin
  agent-orchestration layer on top that treats each LLM call as a Temporal activity.
- **Alternatives**: Airflow/Dagster (batch-oriented, weaker for long-lived
  event-driven workflows with human-in-the-loop waits); a bespoke Postgres-backed job
  queue (simpler initially, but reinvents retries/leases/checkpointing badly over time);
  hosted agent-orchestration SaaS (rejected — conflicts with private-first/no-SaaS-
  dependency-for-core-state requirement).
- **Reason**: Temporal natively provides durable execution, retries, timeouts, signals
  (for approval waits), and versioning — exactly the primitives `08-long-running-
  autonomy.md` requires, self-hostable for privacy.
- **Security consequences**: self-hosted means the workflow state (which can include
  business-sensitive task metadata) stays inside the private boundary; Temporal's own
  mTLS and namespace isolation are used between services.
- **Operational consequences**: adds an operational component to run and monitor;
  mitigated by starting with a single-node deployment for Milestone 0 scale.
- **Vendor lock-in**: moderate (workflow code is written against Temporal's SDK
  semantics); migration path is to re-implement the same durable-execution contracts
  against another engine (Cadence, or a custom implementation) since the workflow
  *logic* doesn't depend on Temporal-specific business features.

## Relational state (structured entities, money, permissions)

- **Selected**: PostgreSQL (self-hosted or private managed instance), encrypted at rest.
- **Alternatives**: MySQL (comparable, weaker JSON/graph-adjacent tooling); a hosted
  multi-tenant DBaaS with broad default network exposure (rejected on privacy grounds
  unless configured private-network-only).
- **Reason**: strongest transactional guarantees (needed for money/permissions), mature
  row-level security for access control, excellent extension ecosystem (pgvector,
  pg_cron), single system reduces operational surface for a single-owner deployment.
- **Security consequences**: row-level security enforces World Model access control at
  the database layer as defense-in-depth beneath the application layer.
- **Operational consequences**: standard backup/replication tooling; well-understood
  failure modes.
- **Vendor lock-in**: low — Postgres is open-source and portable.

## Graph state (relationship traversal)

- **Selected**: model relationships within Postgres initially (adjacency tables +
  recursive CTEs), with pgvector/Apache AGE (Postgres graph extension) evaluated before
  introducing a separate graph database.
- **Alternatives**: Neo4j (excellent graph querying, but a second database system to
  operate/secure/back up at single-owner scale is a real operational cost).
- **Reason**: avoid unnecessary system count for Milestone 0 scale; the entity graph is
  not yet at a size/traversal-complexity where a dedicated graph DB earns its
  operational cost. Revisit if relationship-traversal queries become a bottleneck.
- **Migration path**: World Model service abstracts graph queries behind its own API,
  so swapping the backing store later doesn't require rewriting every caller.

## Vector retrieval (semantic memory)

- **Selected**: pgvector (co-located with the relational store) for Milestone 0–1;
  evaluate a dedicated vector database (Qdrant, self-hosted) if retrieval latency/scale
  demands it.
- **Alternatives**: hosted vector-DB SaaS (rejected by default — confidential/restricted
  embeddings should not leave the private boundary unless the provider offers a
  private/self-hosted deployment).
- **Reason**: minimizes system count early; embeddings generated by a **local embedding
  model** so semantically sensitive content need not leave the private boundary to be
  embedded at all.

## Encrypted object storage

- **Selected**: MinIO (self-hosted, S3-compatible) or a cloud provider's object storage
  with customer-managed KMS keys, depending on deployment target.
- **Reason**: S3-compatibility keeps tooling/migration paths open; customer-managed keys
  ensure the storage provider cannot read content even if compelled.

## Secrets management

- **Selected**: HashiCorp Vault (self-hosted) for the Credential Broker's backing store;
  OS keychain/TPM for owner-device-bound keys.
- **Alternatives**: cloud KMS/HSM (strong option if deployment is cloud-based — evaluate
  per actual hosting choice; not mutually exclusive with Vault, which can use a cloud
  KMS as its unseal mechanism).
- **Reason**: dynamic secrets, short-TTL leases, and fine-grained policy are exactly the
  Credential Broker's requirements; mature audit logging built in.
- **Vendor lock-in**: low — Vault is open-source; secret-consumption pattern (short-lived
  leased credentials) is portable to a KMS-based implementation if needed.

## Policy-as-code

- **Selected**: Open Policy Agent (OPA/Rego) for the Policy Engine's rule evaluation
  (autonomy levels, budget checks, prohibited actions), invoked synchronously by the
  Action Broker.
- **Reason**: deterministic, testable, version-controlled policy separate from
  application code and entirely separate from LLM judgment — critical for the "not
  another LLM judgment call" requirement in `04-agent-architecture.md`.
- **Operational consequences**: policy changes are code review + test-gated changes,
  matching the "owner-approved, versioned" requirement naturally.

## Sandboxing / code execution

- **Selected**: gVisor or Firecracker microVMs for agent task sandboxes; a further-
  isolated ephemeral microVM specifically for code-execution tasks.
- **Alternatives**: plain Docker containers (weaker kernel isolation; acceptable for
  low-risk GREEN tasks, insufficient alone for code execution or AMBER/RED-adjacent
  tasks).
- **Reason**: strongest practical isolation available without dedicated hardware
  virtualization infrastructure; Firecracker is what production multi-tenant code
  execution platforms use for a reason.

## Observability

- **Selected**: OpenTelemetry for tracing/metrics/logs, feeding a self-hosted stack
  (Prometheus + Grafana + Loki) rather than a third-party SaaS observability platform
  by default, to keep operational telemetry (which can leak business-sensitive
  patterns) inside the private boundary.
- **Migration path**: OpenTelemetry's vendor-neutral format keeps a path open to a
  hosted provider later for convenience if the owner accepts that trade-off explicitly.

## Local inference

- **Selected**: Ollama or vLLM (self-hosted) running an open-weight model on
  owner-provisioned hardware, as the local-reasoning-model and embedding-model tier of
  the Model Router.
- **Reason**: mature, well-supported self-hosting tooling; vLLM for higher-throughput
  production use if local inference load grows.

## Private networking

- **Selected**: WireGuard-based mesh (via Tailscale for ease of setup, or self-hosted
  Headscale for full independence from a third-party control plane) for the Secure
  Access Layer between owner devices and the private control plane.
- **Alternatives**: traditional VPN (heavier, less ergonomic for a single-owner
  multi-device setup); public internet + mTLS-only (rejected as sole control — defense
  in depth wants network-layer restriction too, not just app-layer auth).
- **Reason**: strong default-deny posture, easy device onboarding via hardware-backed
  keys, minimal attack surface.
- **Vendor lock-in**: Tailscale's control plane is a third-party dependency for peer
  discovery; Headscale removes that at the cost of self-hosting it. Recommendation:
  start with Tailscale for velocity, document the Headscale migration path in the ADR.

## Browser automation (where needed for research/ops tasks)

- **Selected**: Playwright, sandboxed identically to code-execution tasks (a browser is
  a code-execution surface).

## Summary table

| Layer | Choice | Primary reason |
|---|---|---|
| Orchestration | Temporal | Durable execution primitives match long-running autonomy needs |
| Relational state | PostgreSQL | Transactional integrity + RLS + maturity |
| Graph | Postgres-native → evaluate Neo4j later | Avoid premature system count |
| Vector | pgvector → evaluate Qdrant later | Same |
| Object storage | MinIO / cloud + customer-managed keys | S3-compatible, portable |
| Secrets | HashiCorp Vault | Dynamic short-lived leased credentials |
| Policy | OPA/Rego | Deterministic, testable, non-LLM enforcement |
| Sandboxing | gVisor/Firecracker | Strong isolation for untrusted agent workloads |
| Observability | OpenTelemetry + self-hosted stack | Keep operational telemetry private |
| Local inference | Ollama/vLLM | Mature self-hosting for privacy tier |
| Private networking | Tailscale (→ Headscale path) | Fast, secure, low-friction owner access |
