# GRIDKEEP Cyber OS — Security Findings Register

Tracks every finding from the independent security audit (an adversarial code review that treated all
prior milestone claims, tests, and documentation as unverified until directly checked or reproduced
against a live database) and every finding the production-hardening programme surfaces on top of it.

**Status definitions:**

- **open** — not yet addressed.
- **mitigated** — a fix has shipped and is covered by an executable test, but has not yet been confirmed
  by an independent party (a re-audit, a real pentest) — see Milestone 14 of the hardening programme.
- **accepted** — a deliberate decision not to fix, with a documented business/technical reason. Never used
  to silently hide risk; the reason is always written out.
- **transferred** — the risk is now owned by something outside this codebase (a reverse proxy, a cloud
  provider's IAM boundary, an operational process) and is tracked here only so it isn't forgotten.

Do not delete a resolved row. Change its status and add a dated note instead — this file is the audit
trail of the audit trail.

## Critical

| C-01 | Row-Level Security is inert — the application's Postgres role (`gridkeep`, created via `POSTGRES_USER` on the stock image) is an unrestricted superuser that unconditionally bypasses RLS, `FORCE ROW LEVEL SECURITY` notwithstanding. Reproduced live: an INSERT with a mismatched `app.current_tenant_id` succeeded and committed. | **mitigated (2026-07-19, Milestone 31)** | M3 (Tenant Isolation, PostgreSQL RLS, and Worker Isolation) | Fixed by migration `34016597f04f`, which creates a second, deliberately unprivileged role (`gridkeep_app`: `NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE NOREPLICATION`) and grants it exactly the CRUD access the application needs. `DATABASE_URL` — the connection api/worker/beat actually make every request over — now points at this role in `docker-compose.yml`, `docker-compose.production.yml`, and `.github/workflows/ci.yml`; `DATABASE_MIGRATION_URL` is unchanged and still the superuser, since `migrations/env.py` hard-codes it as the only URL Alembic ever uses (no chicken-and-egg problem: the role that creates `gridkeep_app` is never the role that connects as it). `core/config.py` gained two new fail-closed production checks — refusing to boot if `DATABASE_URL` still contains either the superuser credential or the shipped `gridkeep_app` development password. **Verified**: `gridkeep_app`'s `pg_roles` row confirmed directly (`rolsuper=false`, `rolbypassrls=false`) against a real Postgres cluster built the same way the Docker image bootstraps `gridkeep`; the audit's own live-reproduction attack (an INSERT into `memberships` with a mismatched `app.current_tenant_id`) was re-run manually against this exact role/policy configuration and now fails with `ERROR: new row violates row-level security policy for table "memberships"` and rolls back, where it previously succeeded and committed as the superuser; `alembic upgrade head` → the new migration runs clean end-to-end against a fresh database. Fixing this exposed two tests that were previously passing only *because* RLS did nothing — not new bugs, but pre-existing gaps the superuser bypass had been masking: `test_production_config.py`'s DATABASE_URL credential-check test asserted a stale literal string (the new DATABASE_URL-specific message text changed; the fail-closed refusal itself was always correct), and `test_account_recovery.py::test_account_recovery_cannot_be_approved_by_the_requester_themselves` called the service layer directly against a session with no `app.current_tenant_id` set, which the superuser connection tolerated but the real RLS-enforcing role correctly does not — fixed by setting tenant context before the direct call, matching what the real HTTP route (`get_tenant_db`) already does. Full backend suite: **275/275 passing** on a fresh database (up from 272/275 before these two fixes) — the three pre-existing C-01-attributable failures noted below under "corroborating evidence" are now gone, exactly as predicted, with no code change to the tests or code they exercise beyond what's described above. `ruff check .` clean. **Not yet independently re-verified — pending Milestone 14's external audit, same as every other "mitigated" entry in this register.** — **Original corroborating evidence (2026-07-19, found while verifying Milestone 29)**, preserved for the audit trail: running the full suite against a real local Postgres role built the same way (`initdb -U gridkeep`, matching the Docker image's bootstrap) surfaced three *pre-existing, independent* test failures, all attributable to this same root cause and none caused by Milestone 29's changes: `test_audit.py::test_audit_log_is_append_only_update_has_no_effect` and `::test_audit_log_is_append_only_delete_has_no_effect` (an UPDATE/DELETE that `FORCE ROW LEVEL SECURITY`'s missing policy should silently deny instead succeeded, `rowcount == 1`, not `0`), and `test_attack_surface.py::test_add_domain_already_claimed_by_another_tenant_conflicts` (a cross-tenant domain claim saw the other tenant's row and returned the wrong error message, though it still correctly refused the claim). All three now pass unmodified under the least-privilege role. |
| C-02 | No production credential-vault adapter exists. `core/config.py`'s own comment points at `modules/credential_vault/adapters/production.py`, which does not exist. `get_vault_adapter()` is hardcoded to always return the local adapter regardless of environment, and the local adapter's default master key is a public string committed in this repository. | **mitigated (2026-07-19, Milestone 33)** | M5 (Credential Vault, KMS, Secrets, and Connector Security) | Fixed by `modules/credential_vault/adapters/hashicorp_vault.py`, a real production adapter backed by HashiCorp Vault's Transit secrets engine (encryption-as-a-service — the application never holds, derives, or persists any key material; every `encrypt`/`decrypt` is a real network request to Vault). Chosen over a specific cloud KMS (AWS/GCP/Azure) because it's the one option `adapters/base.py`'s own docstring lists that isn't tied to a single cloud provider, matching this codebase's actual deployment target (self-hosted docker-compose, no cloud account to bind a KMS to). `get_vault_adapter()` (`modules/credential_vault/service.py`) now selects between it and the local adapter based on the new `VAULT_ADAPTER` setting (`local` \| `vault`) — `core/config.py`'s fail-closed validator refuses to boot with `environment=production` and `VAULT_ADAPTER` still `local`, or `vault` without both `VAULT_HASHICORP_ADDR`/`VAULT_HASHICORP_TOKEN` set. `docker-compose.production.yml`'s api/worker/beat services now require all three as `${VAR:?message}`. **Verified against a real, locally-run HashiCorp Vault server (`vault server -dev`), not a mock**: `tests/security/test_vault_adapters.py` (7 cases) starts an actual Vault process as a module-scoped fixture and proves a real encrypt/decrypt round-trip, that the persisted ciphertext never contains the plaintext, correct key-version reporting, that a tampered ciphertext is rejected by Vault's own AES-256-GCM authentication (not this codebase's crypto), that a wrong token and an unreachable server both raise the new `VaultUnavailableError` (503) rather than crashing or hanging, and that constructing a second adapter instance against an already-provisioned key is safe (idempotent create-or-converge, mirroring migration `34016597f04f`'s pattern for the `gridkeep_app` Postgres role). The application's own Vault token is deliberately never granted `sys/mounts` capability — enabling the Transit engine mount is documented as an ops-side provisioning step (`docs/deployment-production.md`, new "Provisioning HashiCorp Vault" section, including the exact least-privilege policy the token needs) since a compromised application token should never be able to reconfigure Vault's engine topology; the application does self-provision its own narrowly-scoped named key on first use, which the documented policy explicitly grants. `.github/workflows/ci.yml` installs the real `vault` binary so this proof runs in CI, not only locally. Full backend suite: **287/287 passing** (up from 277 — 10 new tests: 7 in `test_vault_adapters.py`, 3 in `test_production_config.py`), `ruff check .` clean. **Not yet independently re-verified — pending Milestone 14's external audit, same as every other "mitigated" entry in this register.** This closes the audit's last open Critical finding — both C-01 and C-02 are now mitigated, pending that same external re-verification. |

## High

| ID | Finding | Status | Milestone | Notes |
|---|---|---|---|---|
| H-01 | No rate limiting on `POST /api/auth/mfa/verify-login` — a wrong TOTP/backup-code guess doesn't invalidate the MFA challenge token, allowing unlimited guesses against a 6-digit (10^6) space within the token's 10-minute TTL. | **mitigated (2026-07-19, Milestone 30)** | M2 | Fixed by two independent layers: (1) `modules/identity/routes.py:verify_login_mfa` now calls `login_rate_limiter.check` keyed by the challenge token itself before ever calling `consume_mfa_challenge_token` — 5 requests per token within its 10-minute TTL, then 429. (2) `modules/identity/service.py:consume_mfa_challenge_token` now increments a DB-persisted `MfaChallengeToken.failed_attempts` column on every wrong guess and treats the token as invalid once it reaches `MFA_CHALLENGE_MAX_FAILED_ATTEMPTS` (5) — a durable backstop independent of Redis. Verified by `tests/test_mfa.py::test_mfa_verify_login_rate_limited_after_five_wrong_attempts` (proves the Redis layer) and `::test_mfa_challenge_token_locked_out_after_max_failed_attempts_even_with_the_correct_code` (proves the DB layer in isolation, by driving the counter directly and confirming even the genuinely correct TOTP code is then refused). **Not yet independently re-verified — pending M13's regression suite and M14's external audit, same as every other "mitigated" entry in this register.** |
| H-02 | Cookie `Secure` flag, HSTS presence, and `/api/docs` exposure all keyed off a single `ENVIRONMENT` env var with an insecure (`development`) default and no fail-closed guard. | **mitigated (2026-07-19, Milestone 29)** | M1 | Fixed by: (1) `core/config.py` — a `model_validator(mode="after")` refuses to construct a `production` `Settings` object while any of `VAULT_LOCAL_MASTER_KEY`, `OBJECT_STORAGE_ACCESS_KEY`/`SECRET_KEY`, `DATABASE_URL`/`DATABASE_MIGRATION_URL`, `CORS_ALLOW_ORIGINS`, `REDIS_URL`, or `ALLOW_INSECURE_COOKIES_FOR_LOCAL_DEV` still carries its shipped development value. (2) Session/CSRF cookies are now `Secure` **by default in every environment** (`modules/identity/routes.py:_cookie_secure_kwargs`) — the only way to get an insecure cookie is the new, narrowly-named `allow_insecure_cookies_for_local_dev` opt-out, which the same validator refuses to allow in production. (3) `Strict-Transport-Security` is now sent unconditionally by `SecurityHeadersMiddleware`. Verified by `tests/security/test_production_config.py` (9 cases) and `tests/security/test_security_headers.py` (4 cases, including a real HTTP round-trip asserting `Secure`/`HttpOnly` appear in the literal `Set-Cookie` header). API-docs exposure (`main.py:42-44`) was already correctly gated on `is_production` before this milestone — confirmed unchanged and correct, not re-fixed. **Not yet independently re-verified — status will move to a plain `mitigated` reference in M13's regression suite and to fully closed only after M14's external audit.** |

## Programme-level (not from the original audit — surfaced while building the hardening programme itself)

| ID | Finding | Status | Milestone | Notes |
|---|---|---|---|---|
| P-01 | `docker-compose.production.yml`'s `api` service would have silently inherited the base file's `ALLOW_INSECURE_COOKIES_FOR_LOCAL_DEV: "true"` (Compose merges `environment:` maps key-by-key, unlike `ports`/`volumes`, which this file resets with `!reset`) — caught while empirically verifying the overlay with `docker compose config`, before it ever reached a running container. | mitigated (2026-07-19, Milestone 29) | M1 | Fixed by explicitly setting `ALLOW_INSECURE_COOKIES_FOR_LOCAL_DEV: "false"` in `docker-compose.production.yml`'s `api` environment block, rather than relying solely on `core/config.py`'s boot-time refusal as the only backstop. Verified by running `docker compose -f docker-compose.yml -f docker-compose.production.yml config` with the full set of required production variables and confirming the merged output. |
| P-02 | `core/deps.py:get_platform_context` had no MFA requirement at all — any `is_platform_user` account with just a password could reach every `/api/platform/*` route, including creating/approving its own cross-tenant support-access grants (net of the second-approver rule) and suspending or archiving any tenant outright. The single highest-blast-radius account type in the system had a weaker authentication bar than an ordinary tenant admin, who at least has an opt-in `require_mfa_for_admins` toggle. Separately, none of the three disruptive platform actions (create/approve a support-access grant, change a tenant's status) required step-up re-verification the way their tenant-side equivalents (`approve_action_run`, account-recovery approval) already do. Found during Milestone 4's own design work (Platform-Admin Separation), not in the original audit. | mitigated (2026-07-19, Milestone 32) | M4 (Platform-Admin Separation and Support Access) | Fixed by: (1) `core/deps.py:get_platform_context` now raises `MfaEnrollmentRequiredError` unconditionally for any platform account with `mfa_enabled=False` — no per-tenant opt-out toggle, since there is no tenant to configure it away for a platform-wide account. (2) New `core/deps.py:require_platform_step_up` (the platform-side equivalent of `require_step_up`), wired via `dependencies=[Depends(require_csrf), Depends(require_platform_step_up())]` into `create_support_access_grant`, `approve_support_access_grant`, and `update_tenant_status` in `modules/platform_admin/routes.py`. (3) `modules/identity/routes.py:_compute_mfa_enrollment_required` extended to flag `mfa_enrollment_required` for platform accounts independently of any tenant membership, so `/api/auth/me` and `/api/auth/login` surface the block proactively — needed since a platform-only account has zero tenant memberships and the pre-existing tenant-scoped check always returned `False` for one. Frontend: `app/platform/layout.tsx` redirects to a new `app/platform/security/page.tsx` (MFA enrollment has no tenant-scoped page a platform-only account could otherwise reach), and `app/platform/support-access/page.tsx`/`app/platform/tenants/page.tsx` gained step-up prompts on `step_up_required` errors, mirroring the pattern `app/(tenant)/automation/page.tsx` already uses for `approve_action_run`. Verified by `tests/test_platform_admin.py::test_platform_admin_without_mfa_is_blocked_from_every_platform_route` (a platform account with no MFA gets `mfa_enrollment_required` on both login and the first platform route it tries) and `::test_platform_disruptive_actions_require_step_up` (an MFA-enabled platform account with no recent step-up is refused `step_up_required` on both grant creation and tenant status change); every other test in that file (38 total) now enrolls MFA and performs step-up as part of its own setup, itself proof the gates don't block legitimate use. Full backend suite: 277/277 passing, `ruff check .` clean. Frontend: `eslint`/`tsc --noEmit`/`vitest run` (10/10) clean, `next build` succeeds with `/platform/security` listed as a static route. **Not yet independently re-verified — pending Milestone 14's external audit, same as every other "mitigated" entry in this register.** |
